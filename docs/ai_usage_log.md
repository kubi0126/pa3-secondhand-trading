## 记录 01　需求与设计材料梳理、技术栈选择

- **使用场景**：阅读 PA1 的 31 条需求、PA2 的 8 模块/13 张 UML/15 屏 UI/MySQL 设计，以及 PA3 的 3 页要求，确定实现范围与技术栈。
- **提示要点**：要求逐条对照 REQ 编号，指出本机环境（无 JDK/MySQL）与 PA3 的硬指标（>1500 行、Git 远程、报告要求）。
- **生成结果**：给出 Python + Flask + SQLite + 复用 PA2 视觉规范的方案；列出 8 模块到服务类的映射、7 天排期与风险。
- **优点**：能快速把 31 条需求归并成可实现的服务清单；提前暴露“PA2 没有远程仓库”“报告禁用大模型”两个约束。
- **问题**：最初考虑 Java Swing 以贴合 PA2 的 JVM 部署图，但本机无 JDK，装环境会挤压实现与测试时间。
- **修改优化后的结果**：改用 Python；在 README 第 6 节与报告“实现与设计的差异”中说明理由，保留后续替换 MySQL 的接口边界。

## 记录 02　数据库 schema 与仓储层

- **使用场景**：把 PA2 的 MySQL 8.0 DDL 转成 SQLite，并实现 8 张表的仓储。
- **生成结果**：`schema.sql` 使用 CHECK 约束表达 ENUM；用部分唯一索引实现
  `uk_active_item`、`uk_active_buyer_item`；仓储层按 user/dict/item/reservation/audit/log/request 拆分。
- **优点**：表名、字段、约束与 PA2 基本同名，报告里的“UML→代码”映射清晰；部分唯一索引直接兜底并发。
- **问题**：
  - SQLite 不支持 MySQL 的生成列 + 唯一索引写法，最初照搬会建表失败；
  - `request_log` 的 `request_id` 是主键，重复插入需要 `ON CONFLICT DO NOTHING`；
  - `Database.init_schema` 最初用 `with connect()` 但没有关闭连接。
- **修改优化后的结果**：改为部分唯一索引 + `ON CONFLICT`；`init_schema` 显式 `close()`；
  在 README 中记录 SQLite 与 MySQL 的差异。

## 记录 03　领域模型与状态机

- **使用场景**：按 PA2 类图与两张状态图生成实体、枚举和状态机。
- **生成结果**：8 个 dataclass、4 个枚举；`ITEM_TRANSITIONS` 与 `RESERVATION_TRANSITIONS`
  逐条列出允许转换，禁止转换统一抛 `StateConflict`。
- **优点**：状态规则从服务代码中抽离，单测可直接覆盖允许/禁止转换；与状态图一一对应。
- **问题**：初稿把“已发布→已售出”也写进允许列表，但 PA2 状态图要求先经过“已预约”；另外“已预约→卖家下架”被误列为允许。
- **修改优化后的结果**：删除这两条；补了 11 条允许、7 条禁止的参数化测试，
  见 `tests/test_state_machines.py`。

## 记录 04　预约服务：幂等、乐观锁与事务

- **使用场景**：实现 PA1 中最复杂的 REQ-008/013/017/018/019/023。
- **生成结果**：`ReservationService.create` 使用 `BEGIN IMMEDIATE`，先占位 `request_log`，
  再校验商品状态/版本/60 秒重复，最后插入预约、锁定商品、写日志、标记成功。
- **优点**：把“先到先得 + 幂等 + 版本冲突 + 日志同事务”放在一个事务里；并发测试只允许一条有效预约。
- **问题**：
  - 初稿在事务外检查 `request_log`，两个并发请求可能都通过检查；
  - 命中幂等时直接 `return` 会让事务提交一条 PROCESSING 记录；
  - 60 秒重复预约最初放在唯一索引之后，导致重复请求先撞唯一约束。
- **修改优化后的结果**：把占位与检查移入 `BEGIN IMMEDIATE`；用内部异常 `_AlreadyProcessed`
  让事务回滚后返回首次预约 ID；60 秒检查提前到插入之前。并发测试见 `tests/test_concurrency.py`。

## 记录 05　Web 路由与页面

- **使用场景**：把 PA2 的 15 屏 UI 改造成可操作的 Jinja 页面。
- **生成结果**：6 个蓝图（auth/items/buyer/seller/admin）、16 个模板、CSRF、角色装饰器、分页宏。
- **优点**：复用 PA2 的色板、状态徽章、表格与表单规范；服务端渲染便于直接演示三种角色。
- **问题**：
  - 初稿在路由里写了 `request.app.config`，Flask 的 request 没有 `app` 属性，页面直接 500；
  - “标记交易完成”只有服务方法，卖家页面没有入口，U18 无法演示；
  - 卖家预约页最初只有待确认，已确认的预约看不到完成按钮。
- **修改优化后的结果**：改用 `current_app.config`；卖家预约页增加“待确认/已确认/已完成/全部”标签，
  已确认行提供“标记交易完成”；新增端到端测试覆盖 登录→发布→审核→预约→确认→完成。

## 记录 06　表单校验异常类型不一致

- **使用场景**：测试非法价格、空标题、空拒绝原因时发现接口返回 500，而不是表单错误。
- **生成结果**：`utils.money/text` 最初抛 `ValueError`，路由只捕获 `AppError`，导致异常穿透到 500。
- **优点**：测试及时暴露了“服务层校验”和“Web 层错误处理”的契约不一致。
- **问题**：同一个校验错误，在服务层是 `ValueError`，在 Web 层期望 `ValidationError`，两边语义不统一。
- **修改优化后的结果**：`utils.money/text` 统一抛 `ValidationError`；路由捕获后回显字段错误；
  补了 6 组注册校验与 3 组价格/URL 校验测试。

## 记录 07　统计口径与权限范围

- **使用场景**：实现管理员分类统计、卖家个人统计、买家进行中预约数。
- **生成结果**：`StatService` 提供 `admin_overview/seller_overview/buyer_overview`。
- **优点**：统计与明细使用同一套仓储查询，口径一致。
- **问题**：
  - 管理员“进行中预约”初稿按每个卖家累加，且把历史状态也算进去，数字偏大；
  - 买家“我的预约”页面误用了卖家统计，显示的是该用户作为卖家的预约数。
- **修改优化后的结果**：新增 `ReservationRepository.count_active()`；买家页面改用 `buyer_overview`；
  统计页增加口径说明。

## 记录 08　测试、代码风格与规模统计

- **使用场景**：补齐单元/集成/并发测试，跑 pylint 与 LOC 统计。
- **生成结果**：75 个测试全部通过；覆盖率 81%；pylint 10.00/10（项目 `.pylintrc`）；
  Python 手写代码 3503 行（非空非注释，41 个文件）。
- **优点**：测试覆盖状态机、权限、幂等、并发、违规联动、页面与 CSRF；LOC 统计排除测试/模板/CSS，口径可复核。
- **问题**：
  - 每个测试都重新 seed 4 个 bcrypt cost=12 的账号，测试数增加后仍跑了两分多钟；
  - pylint 初版 8.37，主要是缺文档字符串与“参数过多”等规模告警；
  - `tests/test_web.py` 初期有未使用的导入。
- **修改优化后的结果**：测试环境用 `SECONDHAND_BCRYPT_ROUNDS=4`，耗时降到 10 秒；
  增加 `.pylintrc` 关闭纯规模类告警，保留错误/未使用变量/异常处理检查；清理未使用导入。

## 供报告使用的“不符合预期”案例（建议选 2 个展开）

1. **`request.app.config` 导致 500**：模型把 Flask 的 request 当成有 `app` 属性；实际应使用 `current_app`。
   修正后所有页面可访问。说明模型容易混淆相似 API，必须运行验证。
2. **校验异常类型不一致**：`ValueError` 穿透到 500；统一为 `ValidationError` 后才符合“表单错误回显”的预期。
   说明“生成代码能跑”不等于“错误路径正确”，需要针对异常分支写测试。
3. **卖家完成入口缺失**：服务层有 `complete`，页面没有入口；只看代码不容易发现，走一遍用例才暴露。
   说明要用“用例→页面→服务”的链路核对，而不能只做单元测试。
