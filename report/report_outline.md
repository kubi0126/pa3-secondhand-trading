1. 用浏览器或编辑器打开 `report/report.html`，把每个黄色 `div.todo` 替换为 1–3 个 `<p>` 段落。
2. 图表、表格、命令、测试数据不要改；数字以 `docs/` 下的报告为准。
3. 填完后用文末命令重新生成 PDF，检查分页与图注。
4. 推送 Git 后补第 6.2 节提交号与第 6.3 节仓库截图。

## 各节写作要点

### 1.1 项目与目标（约 250 字）
- 为什么选校园二手交易：高频、状态多、买卖角色可切换。
- PA1 的四个问题：信息分散、是否在售无凭证、预约冲突、过程不可追溯。
- PA3 目标：把“发布—审核—浏览—预约—线下成交”闭环跑通。

### 1.2 对应关系（表格已给，可 100 字）
- 说明 8 个模块都能在代码中找到落点，没有“设计了但没实现”的模块。

### 1.3 技术栈（表格已给，可 80 字）
- 强调 Python/Flask/SQLite 是课程允许的选择，不是偷懒；本机没有 JDK/MySQL。

### 1.4 与实验二的差异（约 200 字）
- MySQL→SQLite、JVM→Python、Nginx→开发服务器、REST→服务端渲染。
- 保留的设计：状态机、唯一约束、乐观锁、日志同事务、分层。
- 如果换回 MySQL/JVM，需要改哪些文件（`schema.sql`、`db.py`、部署方式）。

### 2.1 转换方法（约 300 字）
- 先按类图建实体与仓储，再按状态图写状态机，再按时序图写服务方法，最后按用例图接路由。
- 每完成一块就跑对应测试，避免“写完才发现规则不对”。

### 2.2 13 张 UML 与代码位置（表格已给，可 100 字）
- 说明 13 张图不是全部逐行翻译，类图/状态图/时序图是主要施工图，用例图用于核对入口。

### 2.3 类图 → 实体与仓储（约 250 字）
- 8 个 dataclass、4 个枚举；SQL 只在仓储层；实体不依赖 Flask。
- 为什么 `Item`/`Reservation` 带 `version`。

### 2.4 状态图 → 状态机（约 250 字）
- 8 种商品状态、6 种预约状态；允许/禁止转换集中在一个文件。
- 修改标题/价格/分类回到待审核；已预约只能由取消/拒绝/超时释放；违规下架终态。
- 单测覆盖 11 条允许 + 7 条禁止（商品）、7 条允许 + 4 条禁止（预约）。

### 2.5 时序图 → 创建预约（约 300 字）
- `BEGIN IMMEDIATE` → request_log 占位 → 商品/版本/60 秒校验 → 插入预约 → 锁商品 → 日志 → 标记成功 → 提交。
- 唯一索引兜底并发；版本号兜底旧页面；幂等返回首次结果。

### 2.6 源代码规模（约 120 字）
- 3500 行手写 Python（非空非注释），41 个文件；物理行 4151；模板 1044 行、CSS 496 行另计。
- 已超过 1500 行要求；测试、模板、CSS 不计入门槛。

### 3.1 分层结构（约 180 字）
- 路由只做参数/跳转；服务做用例与事务；仓储做 SQL；领域做状态规则。
- 好处：测试不用起浏览器；换数据库只改仓储/schema。

### 3.2 并发与幂等（约 220 字）
- 先到先得：写事务 + 状态更新 + 部分唯一索引。
- 为什么不用 `SELECT FOR UPDATE`（SQLite 没有行锁；`BEGIN IMMEDIATE` 已串行化写）。
- 幂等：`request_log` 主键占位；重复请求返回首次预约；60 秒重复预约。

### 3.3 事务与一致性（约 180 字）
- 违规下架：取消预约 + 商品下架 + 两条日志同事务；任一步失败回滚。
- 举一个版本冲突导致回滚的例子。

### 3.4 权限与安全（表格已给，可 100 字）
- bcrypt、5 次锁定、角色装饰器、CSRF、参数化 SQL、图片 URL 协议。
- 说明“管理员不参与买卖”的边界。

### 3.5 页面与交互（约 200 字）
- 挑 2–3 个界面：状态徽章、表单错误定位、空状态、窄屏表格横向滚动、危险操作确认。
- 不要只写“美观”，写取舍（信息密度、状态可见性、误操作防护）。

### 4.1 使用方式（约 250 字）
- 给模型上下文：REQ 编号、UML、表结构、分层约定、验收标准。
- 拆任务：schema → 领域 → 仓储 → 服务 → 路由 → 测试。
- 要求先给计划再给代码；每次只改一个模块。

### 4.2 大模型完成的工作（表格已给，可 100 字）
- 说明哪些是模型生成、哪些是自己改的；不要写成“全靠模型”。

### 4.3 不符合预期的案例（约 250 字）
- 从三个案例选两个：`request.app`、`ValueError` 穿透、卖家完成入口缺失。
- 每个案例写：怎么发现（运行/测试/走查）、怎么定位、怎么改、补了什么测试。
- 结论：生成代码必须运行验证，尤其是错误路径。

### 4.4 优缺点与原则（约 300 字）
- 优点：快、覆盖全、能给骨架与测试清单。
- 局限：混淆相似 API、忽略课程约束、错误路径漏、UI/业务取舍需人。
- 原则：先约束后生成，逐行核对，测试兜底。

### 5.1/5.2 运行结果（约 150 字）
- 启动命令、首次建库、演示账号、三种角色走通的流程。
- 遇到的问题：端口占用、数据库重置、CSRF token 过期等（按实际写）。

### 5.3 测试结果（约 180 字）
- 75 passed、81% 覆盖、pylint 10.00、LOC 3500。
- 挑 2–3 个关键测试：并发预约、幂等、违规联动、超时过期。

### 6 Git（约 150 字）
- 分阶段提交：骨架 → 服务 → 页面/测试 → 文档。
- 提交信息用 `feat/fix/docs/test` 前缀；`var/`、`__pycache__` 不入库。
- 推送后补提交号与仓库截图。

### 7 总结（约 350 字）
- 三件事：UML 如何落代码、大模型的有效/无效环节、不足与后续计划。
